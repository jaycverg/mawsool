# Mawsool

Closed-loop referral ticket for mental-health care in Abu Dhabi: a positive screen becomes a time-bound hand-off, and a missed hand-off is visible. A hackathon MVP. The Ticket API (`apps/api`) is the product; three web apps and connectors sit around it.

## Layout

```
apps/api         Fastify + Zod + Drizzle ticket API, staff sign-in, seed
apps/person      PWA, static export (output: 'export'): screening, results, matching, consent, ticket, crisis
apps/clinician   the clinic's queue, the consented ticket detail, the FHIR export (production build behind a strict page policy)
apps/ops         the ops dashboard (funnel, timeliness, crisis, equity) for the ops role, and the demo clock, reset, personas and crisis-number dates for the admin role, and the mock crisis-line console for the crisis_line role
packages/types        Zod schemas and TS types for every entity and contract
packages/instruments  WHO-5, PHQ-9, GAD-7, C-SSRS items, scoring, evaluateCrisis(); SOURCES.md for the wording
packages/rules        match(), deadlines, config.ts (thresholds, windows, crisis numbers, sample insurance table)
packages/ui           tokens, fonts, RTL helpers, platform adapters (storage, notifications, dialler), shared components
packages/consent      the consent element list and redact(): keeps only consented elements, run on the phone before send and again on the server
packages/summary      the only code that may call an LLM: referral-summary prompt over consented elements, template fallback, the Anthropic provider
packages/fhir         the FHIR R4 export built from consented elements, and the vendored official R4 JSON schema it is tested against
infra/           docker-compose.yml        docs/     checklists and the exported spec
```

Workspace packages export TypeScript source (`exports` points at `src/index.ts`); apps transpile them. The API bundles them with tsup.

The browser gates share `scripts/e2e-gate.mjs` and run one spec each (`exit-acceptance.spec.ts`, `phase3-acceptance.spec.ts`, `phase4-acceptance.spec.ts`, `gate-c.spec.ts`). Every spec imports `test` from `apps/person/e2e/fixtures.ts`, which fails a test on any browser console error. A test that provokes a failure on purpose names the exact URL and status (or network error, or blocked address) with `consoleGuard.allow`, for that test alone, and an allowance nothing matched fails; a test that cuts the network (`setOffline(true)`) is excused `net::ERR_INTERNET_DISCONNECTED` and prints each URL it saw; `gate:c` calls `forbidAllowances()` and excuses nothing but the two 404s of `PROVOKES_AN_ERROR` in `gate-c.spec.ts`. A gate with `clinician` or `ops` set also builds that staff app into `.next-e2e` (so a running `pnpm dev` is left alone) and serves the production build; `E2E_GREP=<text>` runs only the tests whose title contains the text, to work on one; a subset run prints that it is not an acceptance result and exits non-zero. The end-to-end API also opens a read-only inspect listener (`apps/api/src/cli/serve-e2e.ts`, a harness, not product API) so a test can read what it stored.

`gate:phase2` installs Chromium on first use, runs on ports 250 above the dev ports, and fails unless the report holds exactly the tests in `apps/person/e2e/acceptance.json`, in both languages. It rebuilds `apps/person/out` with its own API address baked in, so run `pnpm build` again before serving that folder elsewhere. Its registry also holds pixel snapshots of seven screens at 390×844 in both languages, with committed baselines for Chromium on macOS and on Linux (`-chromium-linux.png`, made by `pnpm e2e:linux --update`, which CI uses); a run on another platform fails for want of its own, and `E2E_UPDATE_SNAPSHOTS=1` rewrites them on purpose (never an acceptance result). CI runs the four browser gates in that container; `docs/browser-baselines.md` has the rest. It stays out of `verify` because it downloads a browser and takes minutes; run it before merging anything that touches the person app.

Tests that need a database use in-process PGlite with the real migrations, so `pnpm test` and the `gate:*` commands need no Docker. `pnpm verify` ends with `smoke:dev`, and `smoke:dev` and `db:*` do need Docker.

The API needs `BUNDLE_ENCRYPTION_KEY` (32 random bytes as base64) and refuses to start without one; `.env.example` carries a throwaway key for local development only. `SUMMARY_LLM_ENABLED` is off by default and, when on, also needs `ANTHROPIC_API_KEY`; no key is ever committed.

Second copy of the repo on one machine (for example a gate run from another worktree): set `PORT_OFFSET=100` in its `.env`. Every port moves together (api 4100, apps 3100-3102, Postgres 54429) and the Compose project becomes `mawsool-100`, so containers and volumes never collide.

## Guardrails (enforce in code and tests)

- No AI in scoring, triage or the crisis path. An LLM is used only in `packages/summary`, behind a flag, for the referral summary the person approves. A lint rule (`no-restricted-imports` in `eslint.config.mjs`) and a manifest check fail when anything else imports an LLM SDK; `packages/summary/test/boundary.test.ts` proves it with cases that must fail.
- The crisis path is deterministic and works offline. `packages/instruments` imports nothing but `@mawsool/types` and its own files; a test enforces it. The two optional extras around it never sit on it: the hand-off to the crisis line and the next-day check (below) are separate actions with their own keys, bounded waits and failure outcomes, and `gate:a` stays green with every network entry point stubbed to throw. The crisis screen, its numbers and the block never fail because of either and never wait on the hand-off; releasing the screen waits at most half a second for the next-day schedule to be written and carries on if it is not.
- Minimum data, granular consent, revocation deletes the shared copy. No employer or insurer data path: `apps/api/test/access.test.ts` walks the live route registry, fails on a route nobody reviewed, and refuses every wrong principal on every person and clinician route.
- Equity data is opt-in and coarse: age band, gender, language, region. Aggregates under n = 10 are suppressed. Counting the totals a person sent a clinic in the anonymous symptom-change figures is a separate, default-off opt-in (`persons.outcome_stats_opt_in`): its repeat-check box is disabled until the send box is ticked (UI only; the API also takes it alone, `PUT /me/outcome-statistics`), it covers every total the person sends, Settings turns it off, Delete everything clears it, no clinic-facing read carries it.
- Label every mock (directory, insurance, Malaffi export, TAMM link, messaging, crisis console).
- Arabic and English for every user-facing string. Message files hold all text; a lint rule fails on hard-coded JSX text.
- A phone number is collected only if the person turns reminders on and then chooses to give one (reminders are off by default and the number is optional even then). The server keeps it only in `reminder_phones`, one row per person, AES-256-GCM ciphertext bound to that person (`reminderPhoneContext`), validated by `PhoneNumberSchema`, never on `persons`, tickets, bundles or any screening row; the phone keeps it under its own `reminders` key, never inside a check-in. Turning reminders off, removing the number and Delete everything each delete the server row (turning off waits for the server when a number is held); the phone records `serverMayHoldPhone` before it sends a number and keeps it through any failure, so a lost reply still gets the DELETE, and clears it only on a confirmed 200. Text reminders are a labelled sample that sends nothing, and a number or a reminder's body is never logged. The device registers with a random id and secret; the server keeps only the secret's hash. Every table with a person link needs a reviewed erase path: `apps/api/test/erase-reach.test.ts` fails otherwise.
- A second number can be collected, for the crisis line, and only on the crisis screen: the callback number in the optional hand-off (opt-in, empty by default, `PhoneNumberSchema`). It exists only inside the hand-off's encrypted template in `crisis_handoffs` (AES-256-GCM bound to that row by `crisisHandoffContext`), never on `crisis_events`, `persons`, tickets or bundles, and the phone does not keep it: its records (`crisis:handoff`, a list with one entry per crisis, so a later crisis never hides or overwrites an earlier note) hold only ids and a state, written before the send so a lost reply can still be stopped. The crisis screen decides what to offer from the open crisis's own entry only. The person stops a hand-off from the crisis screen or from Settings, which lists every entry with its own Stop (`DELETE /me/crisis-handoffs/:id` deletes the template and its ledger row and remembers the id in `revoked_handoffs`, in one transaction); Delete everything does the same for every note (`eraseHandoffs`), and the phone adds the ids of every note it ever made, the one whose reply never came included, to the `DELETE /me/data` body (`handoffIds`, optional), so a send the server had not seen yet and that is still on its way is refused too (409 `handoff_stopped`, nothing written). Creating, stopping and erasing take a per-id advisory lock, so a send and a stop at the same instant cannot both miss each other (PGlite has one connection and cannot show it; the race case in `gate:postgres` does). The ledger row is deleted, not revoked, and `revoked_handoffs` holds a random id and the time of the stop with no person, no event and no content, and `sweep` deletes a row an hour after it was written, both on the wall clock (a demo clock step cannot forget a fresh stop or keep an old one): so after a stop or an erase nothing the server keeps ties the person to that crisis event, by id or by time. The event keeps only an anonymous `context_shared` flag and still counts once on the dashboard, and the phone marks a server footprint before any send. Both keys are in the download and are removed by the device wipe (`prefs-and-data.test.ts` walks `KEYS`).
- Reminder text carries no clinical content (no score, band, instrument, condition, service or crisis wording): it is the `reminder` messages and nothing computed, and a test bans clinical words in both languages. A reminder is due one interval (2 or 4 weeks) after the later of turning reminders on and the last finished check-in, on the care clock (`demoNow`). The web cannot schedule a notification in the background, so `ReminderNotifier` shows a due one through the `NotificationAdapter` when the app opens, and the home screen's card carries it until the next check-in.
- Instrument wording comes from published sources only, never machine translation. `wordingStatus: 'verified'` means published validated wording: copied from an obtained source and backed by a cited validation study in `packages/instruments/SOURCES.md`. Everything else is `unverified` and shows a visible label.

## API conventions

- Every route declares `config.access` (`public | person | clinician | ops | admin | crisis_line | inbound | clinic_link`); startup throws if not. A clinician route under `/tickets` must also declare `facilityScoped: true` and use `facilityScopedTicket`.
- **Crisis-line hand-off and console.** `crisis_line` is a staff role (seeded mock operator `crisisline@demo.mawsool.test`, signed in through the ordinary logged link, which opens the ops app's `/<locale>/crisis-line/` console inside `RequireStaffSession` for that role alone). It is allowed on exactly three routes, all under `/crisis-handoffs` (startup throws for a `crisis_line` route anywhere else): `GET /crisis-handoffs`, `GET /crisis-handoffs/:id`, `POST /crisis-handoffs/:id/contact`; `access.test.ts` lists them and refuses the role everywhere else. The person's side is `POST /me/crisis-handoffs` (body `consented: true` literally, the phone's own `handoffId`, `crisisEventId` of an event already on the server, the template: language, trigger, up to three totals, optional callback number; 400 without the consent and nothing written, 409 `crisis_event_unknown` before the event arrives, 409 `handoff_stopped` for an id that was already stopped or erased (the phone then says it was not sent and invites no retry), a repeat of the same id answers 200) and `DELETE /me/crisis-handoffs/:id`. The consent is a ledger row with no ticket, recipient `crisis_line`, element `crisis_handoff` (in `LEDGER_ELEMENTS`, not in `CONSENT_ELEMENTS`, so no ticket screen offers it, and `DELETE /consents/:id` cannot reach it). Every console read joins the ledger and needs the consent live, so a revoked one is 404 even if a row were left; the console is never given a person or crisis event id. "Contact made" stamps the hand-off and completes its `CrisisEvent` on the care clock (confirmed by `mock_line` and resolved, unless the person already confirmed, which keeps its source and time), so the dashboard counts one contact once through `suppress()`; it does not release the phone's block, which only the person releases. Hand-off reads are not audited like bundle reads (the console is a mock). The next-day check is on the phone only: due a day after the person releases the crisis screen, on the care clock, shown as a neutral home card and a notification only if permission was already granted (it never asks), at the guarded, precached `/next-day` screen, whose offer opens the options screen with `?focus=clinic` so the GP and the specialist lead (`clinicFirst`) while the matching, the consent screen and the crisis guard stay the ordinary ones.
- **No-login clinic link** (mock; `access: clinic_link`, only `POST /clinic-link/open` and `/act`, startup throws elsewhere). A facility with `facilities.portal_access = false` (default true; `PUT /facilities/:id/portal-access`, `admin`) is given a one-time link, logged not sent, when a ticket is made at it and after each clinic move that leaves another: `<clinician app>/en/clinic-link/#<ticket id>.<token>`. Credential in the fragment and in request bodies, never in a request URL (the whole link is logged, as the mock delivery); only the token's SHA-256 is stored; 48 h on the wall clock, one ticket and facility, spent by one guarded update inside the move's transaction, so two presses make one move and the other is refused (`gate:postgres` races it). A link that is unknown, altered, used, expired or for another ticket is one 401 `invalid_link` before anything about the ticket; a live one for another facility's ticket is 404, an ended share 410. `open` shows code, tier, state, deadline and open moves and never reads a bundle; `act` fires `acknowledged` or `seen` as the clinic (channel `link`), a refused move (409) spends nothing, and the result's `nextLink` (`issued|not_needed|failed`) tells the page when the next link could not be made (move committed; the page says to contact the service). `sweep` deletes links spent or expired a day ago; Delete everything deletes the person's tickets' links.
- **Context panel** (clinician detail): the trajectory beside the `conditions` element, and, only when conditions are shared and listed, static sample labs (`apps/clinician/lib/sample-labs.ts`) labelled "Sample — would come from Malaffi": clinician app only, never in the API, bundle or FHIR export. Kept-back conditions show "Not shared by the person" and no lab.
- **Anonymous mode** (person app, `lib/anonymous.ts`; details in `docs/anonymous-mode.md`): no request leaves the phone (`deviceFetch()` is the only `fetch`; no registration, directory, clock, crisis event or hand-off), so anonymous crises are not on the dashboard (known gap). The crisis block stays in the ordinary device store, marked `anonymous` (the crisis mark too), never sent or handed over, and never waits on the anonymous database. Check-ins (`screenings`; any other key is refused) are AES-GCM ciphertext under a non-extractable key in the session's own IndexedDB `mawsool-anon-<session id>`, held by a Web Lock while its page lives. The database is deleted whole on leaving, on Delete everything in any mode (one that will not delete never stops the rest: ids are listed first, the device store is cleared regardless, and the person is told), and at the next app start in any tab once its lock has been free for 2 s; another tab's start does not delete it while its page holds the lock (fallbacks and reload grace: the doc). Session ids are listed in the device store (`KEYS.anonymousSessions`) so a browser that cannot list databases can still find them. `/anonymous` is guarded and leaving is refused while a crisis is open. Screens that need the server show an explanation instead (`ANONYMOUS_WALLED_ROUTES`).
- Time comes from `apps/api/src/clock.ts` through an injected `Clock`. Lint forbids `Date.now()` and `new Date()` elsewhere in `apps/api/src`.
- No column defaults to the database clock; the application writes every timestamp.
- Person routes read only the caller's own rows: a ticket that is not theirs is a 404, the same as one that does not exist (`ownedTicket`). Person ticket reads live under `/me/...`; `GET /tickets/:id` and the clinic's event and bundle routes are staff and facility-scoped. Staff routes under `/tickets` must declare `facilityScoped`.
- **Accepted in Phase 3, where the code differs from the spec's endpoint table (behaviour unchanged):** a person reads and acts on their own tickets under `/me/tickets/...`, not `GET /tickets/:id`, so the staff route and the person route can never be confused. Consent is granted inline: `POST /tickets` carries the consent elements and the content for them, and creates the ledger rows with the ticket, instead of taking a consent id made by an earlier `POST /consents`; `POST /consents` only adds one element to a live ticket afterwards. The client sends the hand-off window (`windowDays`) with the ticket, and the API accepts 7 or 14 (`HANDOFF_WINDOWS_DAYS`) for any tier, so the tier-to-window table lives in the matcher on the device and is not re-checked by the server.
- A ticket's state is derived from its `TicketEvent` rows; `tickets.state` is a cache written in the same transaction as the event that claims the next `(ticket_id, seq)`. The unique constraint arbitrates every race: a lost race is a 409 for a request and a no-op for the sweep. The transition table, with who may fire each move, is `src/tickets/transitions.ts`; an illegal move is 409, a move the actor may not make is 403. "Unable to see" is a same-state event with a reason, clinic only.
- **The end of the loop is exact.** The rules are `seen`→`remeasured` (person), `seen`→`closed` (person ending the ticket) and `remeasured`→`closed` (system); any other actor is 403 and any other from-state 409, and nothing else fires `closed`. `remeasured` is fired only by `POST /me/tickets/:id/remeasure` (a plain `{to: 'remeasured'}` event is a 409): it refuses before six weeks after the event that made the ticket `seen` (`remeasureAvailableAt`, care clock; 409 `too_early`) and from any state but `seen` (409), and in one transaction appends `remeasured` (person) then `closed` (system) on the next two sequence numbers; a lost race is a 409 that moves nothing. Its body's `scores` are empty unless the person ticked the box (off by default); its optional `statisticsOptIn` replaces the person's statistics choice in that same transaction (left out, it stays; a refused request changes nothing); and a total whose `takenAt` is before the check opened is a 400 that writes nothing (there is no upper bound: the phone stamps it with its own clock). Totals sent go through `shareRemeasureScores` in the same transaction: if `scores` is not shared a ledger row grants it, and the totals join the bundle's `scores` ciphertext, so a stop, a withdrawal and Delete everything reach them as they reach the rest; a share that no longer exists, or whose stored totals leave no room (`BundleContentSchema` holds 5, while a referral, consent or summary draft is capped at 3 by `ReferralContentSchema`), is a 409 that moves nothing. The sweep never touches `seen`. The funnel's re-measured stage counts tickets that reached `remeasured`; a ticket the person ended from `seen` is loop closed and not re-measured.
- `SharedBundle`, its approved summary and the logged summaries are AES-256-GCM ciphertext (`src/crypto.ts`), bound to their row. Every bundle read checks live consent, redacts again to the consented elements, and writes a `bundle_reads` row. A live `ticket` consent decides a person's withdrawal before the state machine: it ends the share from any state, and from a terminal state changes no state. Revoking one element rewrites the bundle without it and, only if the approved summary was written from that element (the bundle records which elements it was written from, sent as `summaryBuiltFrom`), removes the approved summary and the ticket's logged drafts too; any other summary stays (the response says `summaryRemoved`). Either way it deletes this person's logged rows whose `built_from` holds that element (a draft records the `consented` list it was made from, an approved row the ticket's list), claimed by the ticket or left under its request id; revoking `ticket` empties the bundle, deletes the person's logged drafts that no ticket claimed, and withdraws a live ticket. After it, the staff ticket read and the bundle read both answer 410 (another facility still 404). `sweep` also deletes unclaimed drafts older than 24 hours. Logged summaries are bound to `person:request:kind`. `ticket_events.reason` holds a code from a fixed list (reroute, unable to see, consent revoked), never free text; "unable to see" is its own request (`{unable: true, reason}`), and a same-state move is 409. `DELETE /me/data` does that for everything the person holds.
- **Two clocks** (`docs/two-clocks.md`, with a known sweep gap). Care time (deadlines, the sweep, the day-7 check, ticket events, invite expiry, the metrics' periods, an adverse event's time of occurrence) runs on the care clock; security windows (staff sessions, sign-in links, the signed-request timestamp window, nonce retention, when an adverse event was recorded) always run on the wall clock, so a demo clock jump cannot sign staff out or refuse a good signature. With `DEMO_MODE` unset both are the wall clock; with it set, care time is an `OffsetClock` (`app.careClock`) moved only by `POST /demo/clock/advance` and `POST /demo/reset` (admin access, 404 when the flag is unset). `GET /clock` is always open. The person app and the clinic queue add the offset to the device clock (`demoNow`). The doc has the mechanics (strict flag reading, the `demo_clock` row, the queue, the reset).
- **Metrics** (`src/metrics`, `GET /metrics/funnel|timeliness|crisis|equity|outcomes`, `ops` access only; the detail is `docs/metric-protection.md`). Every published number goes through `suppress()` (under 10, zero included); a share needs its part, its whole and what is left over to reach 10. Cells that add up to a total go through `hiddenCells` / `pinnedCells` (`protect.ts`), which hide cells until no small number can be computed from the published figures of one response; a suppressed cell is `{ suppressed: true }` and nothing else, with one neutral label. The funnel counts journeys and its first two stages are one table; the crisis figures hide what the funnel hides. Equity and the symptom-change figures are each served for ONE period, the last 90 days (`EQUITY_PERIOD`; any other `period` is a 400), the period filter does not reach them, and the Loop closed tile reads equity. Not covered, by decision: later-stage counts subtract, as does a funnel or timeliness cell across two periods.
- **Symptom change** (`GET /metrics/outcomes`, `src/metrics/outcomes.ts`, `docs/outcome-metrics.md`): among tickets that reached `remeasured`, the mean change in PHQ-9 and GAD-7 (repeat total minus referral total) and the shares with reliable improvement or deterioration (`RELIABLE_CHANGE` in `packages/rules/src/config.ts`: PHQ-9 6, GAD-7 4, cited; the threshold counts). Served for the last 90 days only (`EQUITY_PERIOD`). Only totals the person shared (live `ticket` and `scores` consent, bundle not deleted) whose person also has the statistics opt-in on are read, server-side, with no `bundle_reads` row and nothing per ticket returned; any other re-measured ticket is excluded and counted in one figure. Its cells are one protected table, all hidden when the funnel hides its 90-day re-measured stage.
- **Adverse events** (`/adverse-events`, `src/adverse-events`): access `ops` plus `alsoAdmin: true` in the route config (the one way a route admits a second role; startup throws on any other access). A coded type (missed_crisis_follow_up, wrong_routing, data_incident), severity (low to critical), status (open, investigating, closed; only forward moves, else 409), when it happened (care clock, never after now), when it was recorded (wall clock), optionally the keyed pseudonymous ticket id the overdue list shows (`od_` + 12 hex; the server can map it back to a ticket, adding no link beyond that ticket row). No free text and no foreign key to a person, ticket or crisis event, so nothing to erase. Manual only; the crisis path does not depend on it.
- **Metric definitions** (`packages/types/src/metric-definitions.ts`, wording under `defs` in the ops message files, `docs/metric-definitions.md` generated by `pnpm docs:metrics`): every tile and section has an info panel (`InfoPanel`); `metric-definitions.test.ts` fails for a tile with no definition or wording, a stale document, or a field the route's response lacks.
- **Notifier** (`src/notifier`, `docs/messaging.md`): every outbound message (staff sign-in link, clinic link, sample text reminder) goes through one `Notifier`: keyed Arabic and English templates (English when the language is not ours) and a mock driver from `NOTIFIER_DRIVER` (`log`, the default, or `console`; anything else stops the API). Nothing is sent. A record holds the template key, language and channel and, for a text reminder, a keyed hash of the stored number's random row id (`reminder_phones.notify_ref`), never a number, a body or anything computed from the number; the staff and clinic links are logged on purpose, with their link. `POST /me/reminder-phone/sample` hands the person's own stored number a sample reminder on their request and changes no reminder rule. `notifier.test.ts` scans for other log writers and bans clinical words in every template.
- `sweep(db, clock)` (`src/sweep.ts`) appends `overdue` to tickets past their deadline; pg-boss runs it every minute (`src/jobs.ts`). It is idempotent and safe to run concurrently.
- **The directory and the person's ticket are bilingual.** Facilities and services keep English text (`name`, `contact_text`) and, where someone wrote it, Arabic (`name_ar`, `contact_text_ar`, nullable; the seed fills every one, unreviewed by an Arabic speaker). `GET /services?locale=ar|en` (the page's language, the only query the app sends; English when absent) and the person's ticket reads (`/me/tickets...?locale=`, else the language the device registered with) serve the text in that language, and where no Arabic exists they serve the stored English, never a translation. The directory's order is by the English name and then id in both languages, and the matcher's tie-break is the place in that order (it never reads the displayed name), so the language never changes which service is offered. Staff apps still show the English text.
- `/docs` serves the OpenAPI document, generated from the routes' Zod schemas.
- `POST /inbound/screens` (access `inbound`) takes a front door's positive screen and creates an invite, never a ticket. It lives in its own Fastify scope so its JSON parser keeps the raw body the signature covers. `registerInboundAuth` (a `preValidation` hook on every `inbound` route) checks, in order: the source has a key (`INBOUND_KEY_PHC|TAMM|SCHOOL`, at least 32 characters; no key, no source), the timestamp is within 300 s, and the HMAC-SHA256 of `source\ntimestamp\nnonce\nbody` matches. Every failure is the same 401 and writes nothing. The route then spends the nonce and stores the invite in one transaction (`acceptScreen`; `inbound_nonces` purged by the sweep after an hour): a nonce used before is a 401 `replayed`, and a failed write leaves the request retriable. "Delete everything" deletes the invites the person claimed; a ticket keeps its `source`. Only the hash of the claim code is stored (`inbound_invites`). `POST /me/invites/claim` binds an invite to a device in one statement; a code that is unknown, expired or someone else's is the same 404. `POST /tickets` takes an optional `inviteId`: a claimed, unused invite of the caller's sets the ticket's `source` and is recorded; anything else is ignored and the ticket is an app ticket. A reroute never uses one.
- `GET /tickets` is the clinic's queue: its own facility's tickets, earliest deadline first, filtered by state (default the three waiting states) and tier. It applies the same share-ended rule as `GET /tickets/:id` through one SQL condition (`shareEndedSql`): a ticket whose person ended the share is not listed or counted and its detail is 410. A seeded ticket has no consent rows (bar the 35 closed re-measured ones behind the symptom-change tile, for which `runSeed` takes the cipher), so it is listed, its detail is 200 and its bundle and export are 404, never 410. `GET /tickets/:id/fhir` is a bundle read like `/bundle` (`readBundle`: live consent, redaction, audit row) and returns the FHIR R4 Bundle from `@mawsool/fhir`. The approved summary sits under the `ticket` element, so a stop can remove it while the ticket stays live; the detail then shows "no summary" and the export has no note.
- Every API response carries `Cache-Control: no-store`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer` (`plugins/security-headers.ts`). The staff apps (clinician, ops) keep their session in `sessionStorage` and send a page policy from `next.config.ts` (`staffContentSecurityPolicy` in `packages/ui/src/csp.ts`: scripts and connections only to themselves and the API, no framing, no `eval`; inline scripts stay allowed because Next writes its start-up data inline, so `react/no-danger` is an error). Their builds set `NEXT_PUBLIC_ZOD_JITLESS=true`, which `packages/types/src/zod-mode.ts` reads before any schema is built, so Zod does not probe for `eval`.
- A staff screen sits inside `RequireStaffSession` (`packages/ui`): no valid session of an allowed role means a redirect to sign-in and no request for data. The clinician home is the queue. The sign-in page says "not saved" when the browser will not keep the session.
- Staff sign-in links are logged, never sent; one use, 15 minutes, only the hash stored. A clinician's link opens `<CLINICIAN_APP_URL>/en/sign-in/`, an ops or admin link opens `<OPS_APP_URL>/en/sign-in/`; the page spends the token only on a button press.

## Code and commit conventions

- A commit message is one line. No ticket numbers in code comments or product identifiers.
- Tests: a case per recovery branch; prove a guard by deleting it and watching its test fail; no disjunctive assertions.
- The person app stays wrappable as a native app: static export, no server components or actions, platform access only through `packages/ui` adapters.
- `.pnpmfile.cjs` drops Next's optional `@playwright/test` peer, so pnpm does not resolve a second Next.
- The person app keeps everything on the device in an AES-GCM encrypted IndexedDB (`packages/ui/src/platform/encrypted-storage.ts`, key non-extractable), with one deliberate exception: while a crisis is open the tab's `sessionStorage` holds `{trigger, eventId, shownAt}` in plain text (`packages/ui/src/platform/tab-mark.ts`), so a store that refuses or hangs cannot lose the block. It holds no answer, score or person id, and goes when the crisis is resolved, on Delete everything, or when the tab closes. In an anonymous session the tab also holds a random session id (`mawsool.anonymous`; the session's database name carries the same id) and the crisis mark adds `anonymous: true`; none holds an answer, score or result. Settings says both in both languages (`settings.exception`); `phase3-acceptance.spec.ts` asserts the notes' keys and that no answer, score or result sits in page storage. A trigger answer sets a persisted crisis block (`apps/person/lib/crisis.ts`); `CrisisGuard` in the `[locale]` layout sends `GUARDED_ROUTES` (`apps/person/lib/routes.ts`) to `/crisis` until it is resolved. Add a new matching or ticket screen to that list.
- The repeat check (`/remeasure`, a guarded screen that also opens offline) runs through the check-in flow (`?rm=<ticket>&since=<opening ms>`: PHQ-9, then GAD-7, then the totals screen; `since` is what stops an older unfinished check-in being resumed and sent, so every start link carries it), so item 9 fires the crisis path exactly as in any check-in. The ticket offers it from `remeasureOpensAt` (six weeks after the `seen` event, care clock) and offers the person's end control (`seen`→`closed`) whenever the ticket is `seen`.
- The person app's service worker gets its precache list from `apps/person/scripts/build-precache.mjs` after `next build` (pages, built CSS and JS, fonts, manifest, icons, version from the build). To make a screen open offline, add it to `OFFLINE_SCREENS` there. The worker looks a request up ignoring its query string only for a page navigation (`?id=`, a missing trailing slash); any other same-origin request is matched on its whole address, so `/services?locale=ar` never gets the cached `?locale=en` copy when the API is served from the app's own origin (cross-origin requests, the default API address, are not touched at all).
- **The directory is kept on the phone per language** (`apps/person/lib/directory.ts`, key `directory` = `{ ar?, en? }`, each `{ fetchedAt, services }`). Online, a page asks `GET /services?locale=<page language>` and saves that language's copy beside the other's. Offline, a page gets its own language's copy and, with none, the other language's, so matching still works after one online visit in either language: the service names then show in the other language, as stored, never translated, until the next online visit. A copy saved in the old shape (one `{ fetchedAt, services }` with no language) is not read: offline it is no directory (`null`), and the next online visit overwrites it. With no network and no copy at all the directory is `null`. The consent screen disables Send when the service the person chose is not in the directory it loaded (`service === null`) and says so.
- Consent is per element and defaults off, except the required `ticket` element. What the person types for the clinic stays on the phone until they send. A pick that is waiting on consent is kept apart from the current choice (`choice:pending`), and its request id is made once, so a retried send is the same request. "Delete everything" (`apps/person/lib/erase.ts`) sends an unsent crisis record first, then asks the server to remove everything, and stops with nothing deleted if the server holds data and cannot be reached; with nothing ever shared it wipes offline. Erasure wins over an unsent crisis record when it cannot be sent, and the person is told.
- `.local/` (plans, spec, design boards) is git-ignored and lives outside worktrees; read it by absolute path.
