# How long an opt-in lives

Code: `apps/api/src/persons/last-seen.ts`, `apps/person/lib/presence.ts`, `apps/person/lib/server-choices.ts`, `GET /me/opt-ins` (`apps/api/src/routes/person-data.ts`), the sweep (`apps/api/src/sweep.ts`) and `OPT_IN_IDLE_LIMIT_DAYS` in `packages/rules/src/config.ts`; tests: `apps/api/test/opt-in-lifetime.test.ts`, `apps/person/test/presence.test.ts`, `apps/person/test/stored-choice.test.ts`, the browser cases `opted-in-phone-reaches-the-server-once-a-day-so-the-idle-limit-does-not-clear-its-choices`, `settings-says-once-that-the-idle-limit-switched-the-equity-choice-off-and-the-phone-then-sends-nothing-under-it` and `a-background-read-that-gets-401-registers-nothing-and-records-no-day`, `consent.test.ts` and `erase-reach.test.ts`.

A person who clears the browser's site data instead of using Delete everything loses the device secret, and with it the only way to turn their choices off. Without a limit their equity buckets and their anonymous-statistics opt-in would count for ever.

- **What is recorded.** `persons.last_seen_on`, a date with no time: the last UTC day on which a request authenticated as this person (and a repeat registration of the same device), on the wall clock. It is written by one guarded update that changes the row only when its day is older, so at most once a day per person; failing to authenticate writes nothing. A person who registered before the column existed was given the day of the migration. A seeded person has no date (no device), and is left alone.
- **What counts as use.** Any request that authenticates as the person, and nothing else. Opening the app, the home screen, a check-in and Settings make none, so while the equity or the statistics choice is on the app makes one itself: when it starts (and when the browser comes back online), at most once a UTC day on the phone's wall clock, it reads the person's own two choices (`GET /me/opt-ins`, person access, the caller's own row only, `{ equityOptIn, outcomeStatsOptIn }` and nothing else; the day it last did so is the phone's `server:last-seen-sent` note, written only after the read went through). It does nothing when neither choice is on, in an anonymous session (no request leaves the phone there), while a crisis is open (it never sits on or beside the crisis screen), or when the browser says it is offline. A failure is silent: nothing is logged or shown, the day is not noted, and the next start or the return of the network tries again. Code: `apps/person/lib/presence.ts`, started from `DeviceSync`.
- **A background read never registers the phone.** The daily read, and the read Settings makes when it opens, use the credential the phone already holds (`callServerInBackground`): they never make an identity, never register the device and never register it again. A phone the server has forgotten (a rebuilt database, a demo reset) answers 401; the read then changes nothing on the phone, writes no day, and ends as `not_recognised`, so a call nobody made cannot turn the phone into a new person. A call the person makes themselves (`callServer`: sending a referral, Settings' own buttons) keeps registering the phone and asking once more after a 401.
- **What still does not count.** A phone that is only ever used offline for six months, a phone opened only in an anonymous session (it holds no choice to keep), and a phone whose choices were turned on but which is never started again. Their choices turn off, as for a cleared browser. A person who looks at the app daily on a phone that is online keeps both choices for as long as they use it.
- **What the sweep does.** For a person whose last day is `OPT_IN_IDLE_LIMIT_DAYS` (180, about six months) or more behind the wall-clock day, the sweep turns both opt-ins off and deletes the four equity buckets. The day the limit falls on counts: a person last seen 179 days ago keeps their choices, one last seen 180 days ago does not. It runs every minute with the other clean-ups.
- **Wall clock, not care clock.** A demo clock jump neither moves the date nor makes anyone look idle; the sweep reads the security clock for this, as it does for sessions and nonces.
- **Delete everything** clears the date with the rest (the person is gone from the device, so there is nothing to date).
- **What the person is told.** Settings says, beside each opt-in, in Arabic and English, that the choice turns itself off if this phone is not used for 6 months.
- **The phone learns what the server cleared.** The read of the two choices is also how a phone finds out that the sweep switched one off. The next time it reaches the server (the daily read, or the read Settings makes whenever it opens online while a choice is on, whichever comes first), `reconcileChoices` (`apps/person/lib/server-choices.ts`) turns off, on the phone, each choice the phone has on and the server has off (the equity choice also drops the four buckets the phone kept), inside the store lock, judging each note by its value at that moment. **It never turns a choice on**: a server that says on and a phone that says off is left alone, and the only way a choice comes back on is the person turning it on again (the consent screen for group totals, the repeat check's box for statistics). A read that fails, is refused, or answers something other than the two choices changes nothing and records no day; a note the store refuses to turn off ends the read as failed, so the next start tries again.
- **A choice only the phone remembers is checked before it is sent.** Both sending screens pre-tick the box from the phone's note, and the daily read may not have run or may have failed (the app opened offline, the consent page loaded directly). So a `true` that comes only from the stored note, with the box not ticked by the person on that screen, is never sent before the phone asks the server (`confirmStoredChoice`, a foreground `GET /me/opt-ins` made because the person pressed send, which may register the phone as any call they make does): `sendEquityChoice` for the group totals and `finishRepeatCheck` (`statisticsSource: 'noted'`) for the statistics. The server holds the choice: the `true` goes. The server has it off: nothing on is sent, the phone's note is turned off, the box is unticked and the screen says so in the page's language (`consent.equityCleared`, `remeasure.choiceCleared`; on the consent screen the note also says the referral has not been sent yet and to press Send again, and is scrolled into view, since the Send button is far below the box; the repeat check's note sits in the Finish bar), and ticking it again is the person turning it on (that `true` goes as ticked on the screen). The server cannot be asked, or answers something unusable: nothing on is sent either, the box is unticked and the screen says it could not be checked (`equityUnread`, `choiceUnread`). In both cases the screen sends no choice at all until the person ticks it again (the server's choice is left alone, not set to off). A `false`, or no choice, is never held back.
- **A read that overlaps a send cannot undo it.** A send that can turn a choice on (`sendEquityChoice`, `finishRepeatCheck` with a choice) brackets itself with marks in the store (`server:choice-sends`, per choice: a generation that goes up when the send starts and when it ends, and the time it started while it is under way). A read takes the marks before its request; when its answer arrives, `reconcileChoices` leaves a choice alone if a send on it started, ended or is still under way since (the answer may predate it), so the phone never ends with the choice on at the server and off in Settings, where it could not be turned off. A mark older than two minutes is taken as abandoned (a tab closed mid-send) and blocks nothing; marks are stamped and compared on the wall clock only, never the screens' care clock, so a demo clock jump can neither keep an abandoned mark pending nor make a live one look abandoned. A read that starts after a send has begun is covered by the pending mark alone (its snapshot of the generation already holds the send's start). A send whose start mark cannot be written is not made.
- **Settings says so, once.** When the choice that was turned off was turned off for idleness, Settings shows a note in the page's language (`settings.optInsClearedEquity`, `optInsClearedStatistics`, `optInsClearedBoth`): the choice was turned off because the phone was not used for 6 months (and, for group totals, that the details were deleted from the server), and it can be turned on again. The reconcile leaves the note (`server:opt-ins-cleared`, the choices it covers); Settings takes it, which removes it, so a second visit says nothing. Idleness counts as the reason only when the phone's own last confirmed reach of the server (`server:last-seen-sent`, read before today is written) is `OPT_IN_IDLE_LIMIT_DAYS` or more behind. With no such day (the phone never recorded a reach) or a recent one, the choice is corrected without the note, since six months of silence would be the wrong reason (a statistics choice noted "may be on" before a send that never arrived is the case; a phone that last reached the server before this day was kept goes without the note too). A store that will not keep the note still turns the choice off.
- **Not covered.** A person who signs in again does not get their choices back. A phone that is offline, or whose app is not opened, learns nothing until it next reaches the server; until then it still shows the choice on in Settings, but it cannot send a stale `true`, because a send first asks the server. The marks of a send are per tab's store, not locked across tabs: a read in one tab and a send in another are covered only through the shared store's generation, not by a lock. No clinic-facing read carries any of this.
