# Care time, wall time and the demo clock

Moved here from `CLAUDE.md`, where a short version stays. The code is `apps/api/src/clock.ts`, `src/demo/` and `src/jobs.ts`; the tests are `clock.test.ts`, `demo-clock.test.ts` and `lint-clock.test.ts`.

Care time (deadlines, the sweep, the day-7 check, ticket events, invite expiry, the metrics' periods) runs on the care clock; security windows (staff sessions, sign-in links, the signed-request timestamp window, nonce retention) always run on the wall clock, so a demo clock jump cannot sign staff out or refuse a good signature. With `DEMO_MODE` unset (read strictly: `true` or `1` is on, unset, empty, `false`, `0` is off, anything else stops the API) both are the wall clock. With it set, `buildApp` builds an `OffsetClock` for care time; `app.careClock` hands it to the sweep job. The offset is kept in the one-row `demo_clock` table (`src/demo/clock-store.ts`): `buildApp` reads it once at start (only with the flag on; with it unset the row is left alone), the advance route writes the new offset before it moves the clock (moves and the reset run one at a time on one queue, `createClockMover`, so two at once both count, and a reset cannot start between an advance's write and the sweep the advance runs at its new date, nor overlap its write; a failed write leaves the clock where it was). The every-minute pg-boss sweep is not on that queue and can still straddle a reset: a known gap, not closed here. The reset zeroes the clock first, so a sweep that starts during the reload reads the fresh seed at real time, and its reload truncates the row with every other table in one transaction; if the reload fails it rolls back, the row keeps the previous value, and the clock is put back to it. `GET /clock` is always registered, open, holds no person data and returns `{ demoMode, offsetMs }` (a 404 would log a browser console error); only `POST /demo/clock/advance` (+7 days, +3 weeks, +6 weeks, then a sweep at the new time) and `POST /demo/reset` are demo routes: `admin` access, 404 when the flag is unset. The person app and the clinic queue add the offset to the device clock (`demoNow` in `packages/ui`); the person app keeps the last offset in its store and never awaits the read. Reset reloads the seed anchored on the start of today (Dubai), keeps staff sessions, zeroes the offset and makes Noura's TAMM invite through `createInvite`; a phone whose person it deleted registers again on the next 401 (`callServer`) and drops a ticket the server answers 404 for.

## Mechanics of the demo clock

- `DEMO_MODE` is read strictly: `true` or `1` is on; unset, empty, `false` and `0` are off; anything else stops the API. With it unset both clocks are the wall clock.
- With it set, `buildApp` builds an `OffsetClock` for care time (`app.careClock` hands it to the sweep job). The offset is kept in the one-row `demo_clock` table and moved only by `POST /demo/clock/advance` (+7 days, +3 weeks, +6 weeks, then a sweep at the new time) and `POST /demo/reset` (admin access, 404 when the flag is unset), which run one at a time on one queue (`createClockMover`).
- `GET /clock` is always registered and open, holds no person data and returns `{ demoMode, offsetMs }`.
- The person app and the clinic queue add the offset to the device clock (`demoNow` in `packages/ui`).
- Reset reloads the seed anchored on the start of today (Dubai), keeps staff sessions, zeroes the offset and makes Noura's TAMM invite through `createInvite`. The seed's re-measured tickets that carry consents and bundles are stored with the API's own bundle cipher, so the reset takes it.
