# The no-login clinic link (mock)

Moved here from `CLAUDE.md`, where a short version stays. The code is `apps/api/src/clinic-links/service.ts`, `routes/clinic-links.ts` and the clinician app's `ClinicLinkScreen`; the tests are `apps/api/test/clinic-links.test.ts`, `apps/clinician/test/clinic-link.test.ts` and the Phase 4 browser cases.

`access: clinic_link`, only `POST /clinic-link/open` and `POST /clinic-link/act` (startup throws for any other route). A facility with `facilities.portal_access = false` (default true; `PUT /facilities/:id/portal-access`, `admin`) is given a one-time link, logged not sent, when a ticket is made at it and after each clinic move that leaves another: `<clinician app>/en/clinic-link/#<ticket id>.<token>`.

- **Where the credential travels.** In the fragment and in request bodies, never in a request URL. The whole link is logged, as the mock delivery (the notifier's record, see `messaging.md`); the API's request log carries only the route pattern (`request-log.md`), so a token or ticket id never reaches a request line.
- **What is stored.** Only the token's SHA-256. The link is bound to one ticket and the facility that ticket is addressed to.
- **How long it lives.** As long as the hand-off window the ticket serves, 7 or 14 days, counted on the wall clock from the moment the link is made (`clinicLinkLifetimeMs(handoffWindowDaysOf(ticket))`). The window is not stored; it is recovered from the ticket's dates (the whole days from issue to deadline, the largest allowed window that fits, the fallback window otherwise). A link made after a clinic move gets the same window from its own moment. A demo clock jump neither ends a link nor keeps one alive.
- **How it is spent.** By one guarded update inside the move's transaction, so two presses make one move and the other is refused (`gate:postgres` races it, 30 rounds over two connections; the race does not depend on the lifetime).
- **What it refuses.** A link that is unknown, altered, used, expired or for another ticket is one 401 `invalid_link` before anything about the ticket; a live one for another facility's ticket is 404, an ended share 410.
- **What it shows and does.** `open` shows code, tier, state, deadline and open moves and never reads a bundle; `act` fires `acknowledged` or `seen` as the clinic (channel `link`). A refused move (409) spends nothing. The result's `nextLink` (`issued|not_needed|failed`) tells the page when the next link could not be made (the move is committed; the page says to contact the service).
- **Clean-up.** `sweep` deletes links spent or expired a day ago (`CLINIC_LINK_KEEP_MS`); Delete everything deletes the person's tickets' links.
- **The page and the browser's history.** The page reads the fragment once into memory and then replaces its history entry with the same path and query and no fragment (`history.replaceState`, `dropFragment`), so the token and the ticket id are not left in the address bar, in the browser's history or in an address copied afterwards. A reload therefore has no credential and shows the missing-link answer; the clinic opens the link again from where it was given. The Phase 4 browser case asks the browser for its navigation history and finds no id or token in any entry.
