# The optional hand-off to the (mock) crisis line

Moved here from `CLAUDE.md`, where a short version stays. Code: `apps/person/lib/crisis-handoff.ts`, `apps/api/src/crisis-handoffs/service.ts` and `routes/crisis-handoffs.ts`, the ops app's crisis-line console. The route and access rules for the console itself are in `CLAUDE.md` (API conventions).

A second number can be collected, for the crisis line, and only on the crisis screen: the callback number in the optional hand-off (opt-in, empty by default, `PhoneNumberSchema`).

- **What the note holds.** The language, the reason the crisis screen opened (the trigger), up to three totals and, only if the person typed one, the callback number. A total is an instrument and a total, nothing else: the console shows exactly that, so the band and the time of the check-in are neither sent nor stored. An older copy of the app that still sends them has them dropped on arrival; a note stored before the change is read back without them.
- **Where the number lives.** Only inside the hand-off's encrypted template in `crisis_handoffs` (AES-256-GCM bound to that row by `crisisHandoffContext`), never on `crisis_events`, `persons`, tickets or bundles. The phone does not keep it: its records (`crisis:handoff`, a list with one entry per crisis, so a later crisis never hides or overwrites an earlier note) hold only ids and a state, written before the send so a lost reply can still be stopped. The crisis screen decides what to offer from the open crisis's own entry only.
- **Waiting.** The send and the stop never wait for ever on a store or a network that has stopped answering. Each step has a bound (`HANDOFF_STORE_PATIENCE_MS`, 2 s for the phone's store, and `HANDOFF_NETWORK_PATIENCE_MS`, 15 s for the crisis queue's flush and for the call), and a step that runs out ends in an outcome the screen already has: `failed` when the store did not answer before the send (nothing was sent), `offline` when the crisis queue did not flush in time (nothing was sent), `unconfirmed` when the call itself got no answer after the request was issued, and `sent` or `rejected` as before when only the bookkeeping after the answer ran out. **`unconfirmed` does not say nothing was sent**, because once the request has been issued the phone cannot know the note did not arrive: it covers the patience running out, the call's own ten second limit, a connection that drops with the request on its way (or the reply lost), and a server error. The panel says the phone could not confirm the note arrived, that the numbers above still work and that the note can still be stopped (`crisis.handoffNotConfirmed`, both languages), and the `sending` record stays so the stop control is offered and a retry reuses its id. The words that say nothing was sent are kept for the outcomes where that is certain, because nothing left the phone or the server refused it: `offline` (the browser reports no network, the crisis queue could not be flushed, the phone could not register or holds no credential; no record is kept), `failed` (the phone could not prepare the note, or its store did not answer), `stopped` (409 `handoff_stopped`) and a refusal. `offline` and `failed` hold for a first attempt only: a retry finds the earlier attempt's record, which may have arrived, so at the exits where nothing left the phone this time (`offline`'s and `failed`'s) it says `unconfirmed` and keeps the record and its Stop. The earlier record is known from the store or, when the store will not answer that read, from the crisis screen, which already holds it and tells the send (`earlierRecordHeld`). The panel keeps the list it last read when a later read of the store fails or does not answer within the store's patience (`reloadHandoffs`), and it also keeps in memory, per crisis, the record of its own send from the moment the request is issued (`HandoffMemory`, fed by `SendDeps.onIssue`) until the attempt ends in a refusal (`offline`, `not_ready`, `rejected`, `stopped`) or the server confirms a stop. It shows the store's records together with these and tells the next send an earlier attempt exists from both, so a store that breaks, or never answers a read again, even before the panel has read the record it wrote, never hides Stop and never makes the next retry look like a first attempt; Stop works from the remembered id, because the server's delete is what stops the note (if the store then cannot drop its record the person is told to try again, and the next stop finds the server has none and closes it). The memory is the screen's own copy, never written anywhere, and gone with the page; after a reload the panel depends on the store again. A refusal and `stopped` stay as they are. The one cost of this is a phone that is truly offline but still reports a network: its send reads as unconfirmed, and the stop control then finds nothing on the server and closes the record. A step that was given up on may still finish later; the record it leaves is a `sending` one, which stop and retry both handle. The crisis screen, its numbers and the block never wait on any of this.
- **Stopping.** The person stops a hand-off from the crisis screen or from Settings, which lists every entry with its own Stop (`DELETE /me/crisis-handoffs/:id` deletes the template and its ledger row and remembers the id in `revoked_handoffs`, in one transaction). Delete everything does the same for every note (`eraseHandoffs`), and the phone adds the ids of every note it ever made, the one whose reply never came included, to the `DELETE /me/data` body (`handoffIds`, optional), so a send the server had not seen yet and that is still on its way is refused too (409 `handoff_stopped`, nothing written).
- **Races.** Creating, stopping and erasing take a per-id advisory lock, so a send and a stop at the same instant cannot both miss each other (PGlite has one connection and cannot show it; the race case in `gate:postgres` does).
- **What the server keeps afterwards.** The ledger row is deleted, not revoked, and `revoked_handoffs` holds a random id and the time of the stop with no person, no event and no content. `sweep` deletes a row an hour after it was written, both on the wall clock (a demo clock step cannot forget a fresh stop or keep an old one): so after a stop or an erase nothing the server keeps ties the person to that crisis event, by id or by time. The request log carries no hand-off id either (`request-log.md`). The event keeps only an anonymous `context_shared` flag and still counts once on the dashboard, and the phone marks a server footprint before any send.
- **On the phone.** Both keys are in the download and are removed by the device wipe (`prefs-and-data.test.ts` walks `KEYS`).
