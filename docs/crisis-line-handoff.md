# The optional hand-off to the (mock) crisis line

Moved here from `CLAUDE.md`, where a short version stays. Code: `apps/person/lib/crisis-handoff.ts`, `apps/api/src/crisis-handoffs/service.ts` and `routes/crisis-handoffs.ts`, the ops app's crisis-line console. The route and access rules for the console itself are in `CLAUDE.md` (API conventions).

A second number can be collected, for the crisis line, and only on the crisis screen: the callback number in the optional hand-off (opt-in, empty by default, `PhoneNumberSchema`).

- **What the note holds.** The language, the reason the crisis screen opened (the trigger), up to three totals and, only if the person typed one, the callback number. A total is an instrument and a total, nothing else: the console shows exactly that, so the band and the time of the check-in are neither sent nor stored. An older copy of the app that still sends them has them dropped on arrival; a note stored before the change is read back without them.
- **Where the number lives.** Only inside the hand-off's encrypted template in `crisis_handoffs` (AES-256-GCM bound to that row by `crisisHandoffContext`), never on `crisis_events`, `persons`, tickets or bundles. The phone does not keep it: its records (`crisis:handoff`, a list with one entry per crisis, so a later crisis never hides or overwrites an earlier note) hold only ids and a state, written before the send so a lost reply can still be stopped. The crisis screen decides what to offer from the open crisis's own entry only.
- **Waiting.** The send and the stop never wait for ever on a store or a network that has stopped answering. Each step has a bound (`HANDOFF_STORE_PATIENCE_MS`, 2 s for the phone's store, and `HANDOFF_NETWORK_PATIENCE_MS`, 15 s for the crisis queue's flush and for the call), and a step that runs out ends in an outcome the screen already has: `failed` when the store did not answer before the send (nothing was sent), `offline` when the network did not (the `sending` record stays, so the note can still be stopped and a retry reuses its id), and `sent` or `rejected` as before when only the bookkeeping after the answer ran out. A step that was given up on may still finish later; the record it leaves is a `sending` one, which stop and retry both handle. The crisis screen, its numbers and the block never wait on any of this.
- **Stopping.** The person stops a hand-off from the crisis screen or from Settings, which lists every entry with its own Stop (`DELETE /me/crisis-handoffs/:id` deletes the template and its ledger row and remembers the id in `revoked_handoffs`, in one transaction). Delete everything does the same for every note (`eraseHandoffs`), and the phone adds the ids of every note it ever made, the one whose reply never came included, to the `DELETE /me/data` body (`handoffIds`, optional), so a send the server had not seen yet and that is still on its way is refused too (409 `handoff_stopped`, nothing written).
- **Races.** Creating, stopping and erasing take a per-id advisory lock, so a send and a stop at the same instant cannot both miss each other (PGlite has one connection and cannot show it; the race case in `gate:postgres` does).
- **What the server keeps afterwards.** The ledger row is deleted, not revoked, and `revoked_handoffs` holds a random id and the time of the stop with no person, no event and no content. `sweep` deletes a row an hour after it was written, both on the wall clock (a demo clock step cannot forget a fresh stop or keep an old one): so after a stop or an erase nothing the server keeps ties the person to that crisis event, by id or by time. The request log carries no hand-off id either (`request-log.md`). The event keeps only an anonymous `context_shared` flag and still counts once on the dashboard, and the phone marks a server footprint before any send.
- **On the phone.** Both keys are in the download and are removed by the device wipe (`prefs-and-data.test.ts` walks `KEYS`).
